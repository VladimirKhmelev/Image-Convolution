# Image Convolution

Свёртка изображений с фильтрами 3×3–9×9, 4 стратегиями CPU-параллелизации и поддержкой композиции ядер.

## Быстрый старт

```bash
# применить фильтр (последовательно)
./gradlew run --args='photo.png "Gaussian Blur 3×3" --output result.png'

# применить фильтр параллельно
./gradlew run --args='photo.png "Gaussian Blur 3×3" --strategy rows --output result.png'

# цепочка фильтров — три прохода
./gradlew run --args='photo.png "Gaussian Blur 3×3" "Sharpen 3×3" "Edges 5×5" --output result.png'

# цепочка фильтров — составное ядро (один проход)
./gradlew run --args='photo.png "Gaussian Blur 3×3" "Sharpen 3×3" --compose --output result.png'

# бенчмарк всех стратегий
./gradlew run --args='photo.png --benchmark'

# бенчмарк цепочки + сравнение с составным ядром
./gradlew run --args='photo.png "Gaussian Blur 3×3" "Gaussian Blur 5×5" --benchmark --compose --csv results.csv'
```

## Тесты

```bash
./gradlew test
```

Отчёты: `build/reports/tests/test/index.html`, `build/reports/jacoco/test/html/index.html`

## Фильтры

24 фильтра четырёх размеров. Каждый размер содержит одинаковый набор типов:

| Размер | Оп/пиксель | Типы                                                      |
|--------|------------|-----------------------------------------------------------|
| 3×3    | 9          | Identity, Box Blur, Gaussian Blur, Sharpen, Edges, Emboss |
| 5×5    | 25         | то же                                                     |
| 7×7    | 49         | то же                                                     |
| 9×9    | 81         | то же                                                     |

## Стратегии параллелизации

| Ключ     | Описание                                         |
|----------|--------------------------------------------------|
| `seq`    | Последовательный — один поток, строка за строкой |
| `pixels` | По пикселям — N чанков, каждый поток свой чанк   |
| `rows`   | По строкам — строки делятся между потоками       |
| `cols`   | По столбцам — столбцы делятся между потоками     |
| `grid`   | По сетке — 2D-разбиение на R×C ячеек             |

Дополнительные флаги: `--threads N`, `--grid-rows R`, `--grid-cols C`, `--tile-size T` (размер тайла в пикселях, подбирает сетку под кэш).  
Все числовые флаги поддерживают оба синтаксиса: `--threads 4` и `--threads=4`.

### Композиция ядер (`--compose`)

Флаг `--compose` математически сворачивает переданную цепочку ядер в одно и применяет его за один проход.  
Например, `"Gaussian Blur 3×3" "Gaussian Blur 5×5" "Gaussian Blur 7×7" --compose` строит ядро 13×13 вместо трёх отдельных проходов по изображению.

Плюс: меньше проходов по памяти. Минус: составное ядро больше — операций на пиксель больше.  
Когда выгодно — зависит от размера изображения и стратегии, подробнее в разделе «Производительность».

### Задача 1 — последовательный референс

Фильтр: **Gaussian Blur 3×3**, один поток.

![sequential](plots/sequential/time_vs_size.png)

Время линейно по числу пикселей — O(W·H·K²). Это базовый результат, относительно которого считается ускорение параллельных стратегий.

### Задача 2а — стратегии параллельности

Фильтр: **Gaussian Blur 3×3**.

![overall](plots/strategies/overall_chart_Gaussian_Blur_3×3.png)

#### 128×128 — оверхед корутин

На маленьком изображении параллельные стратегии **медленнее** последовательной: стоимость запуска корутин и синхронизации превышает объём работы. Сетка выигрывает за счёт меньшего числа реально запускаемых задач.

![128x128](plots/strategies/128x128_chart.png)

#### 7071×7071 — кэш-катастрофа

«По столбцам» (881 мс) почти не отличается от последовательного (1245 мс) — каждый шаг по вертикали даёт промах кэша, параллелизм не помогает (×1.41). «По строкам» и «По сетке» дают ~4.5–4.7×.

![7071x7071](plots/strategies/7071x7071_chart.png)

Остальные размеры (512×512, 1920×1920, 3000×3000) разобраны в [`plots/README.md`](plots/README.md).

#### Почему «По столбцам» медленнее «По строкам»

Пиксели изображения хранятся строка за строкой. При обходе по строкам процессор читает память последовательно и успевает подгружать следующие данные заранее. При обходе по столбцам каждый следующий пиксель находится на целую строку изображения дальше в памяти — процессор вынужден ждать загрузки каждого пикселя отдельно. На больших изображениях это даёт ~3–5× проигрыш относительно построчного обхода.

### Задача 2а — масштабируемость по числу потоков

Фильтр: **Gaussian Blur 3×3**, потоки: 1, 2, 4, 8, 12.  
Speedup считается относительно последовательного из того же запуска бенчмарка.

| Размер    | Стратегия    | t=1   | t=2   | t=4   | t=8   | t=12  |
|-----------|--------------|-------|-------|-------|-------|-------|
| 1920×1920 | По строкам   | ×0.92 | ×1.78 | ×3.15 | ×3.06 | ×4.51 |
| 1920×1920 | По столбцам  | ×0.53 | ×1.05 | ×1.94 | ×1.66 | ×2.66 |
| 7071×7071 | По строкам   | ×0.87 | ×1.66 | ×3.29 | ×4.27 | ×4.74 |
| 7071×7071 | По столбцам  | ×0.37 | ×0.65 | ×0.85 | ×0.80 | ×0.97 |

При одном потоке все параллельные стратегии **медленнее** последовательного — накладные расходы на запуск корутин и барьер `awaitAll` не окупаются на одном потоке.

#### 128×128 — оверхед не даёт масштабироваться

На маленьком изображении прирост от добавления потоков минимален: даже при 12 потоках лучшие стратегии едва превышают ×2. Стоимость синхронизации сопоставима с объёмом работы.

![128x128_scaling](plots/scaling/128x128_scaling.png)

#### 7071×7071 — кэш-промахи сводят на нет параллелизм

«По столбцам» при одном потоке даёт ×0.37 — в 2.7× медленнее последовательного из-за кэш-промахов на каждом шаге. При 12 потоках speedup едва достигает ×1: добавление потоков не спасает, когда каждый поток упирается в память. «По строкам» и «По сетке» масштабируются нормально, но насыщаются около ×4.7.

![7071x7071_scaling](plots/scaling/7071x7071_scaling.png)

Все графики: [`plots/scaling/`](plots/scaling/).

### Задача 2b — композиция ядер

Цепочка: **Gaussian Blur 3×3 → 5×5 → 7×7**. Сравниваются:
- последовательное применение — 3 прохода, 83 операции на пиксель
- составной фильтр 13×13 — 1 проход, 169 операций на пиксель

![overall_compose](plots/compose/overall_compare.png)

#### 128×128 — составной выигрывает

Изображение целиком помещается в кэш. Один проход с большим ядром быстрее трёх: по строкам 1.44 мс vs 2.01 мс. Однопоточно составной в 1.7× **медленнее** — без параллелизма лишние операции не окупаются.

![128x128_compose](plots/compose/128x128_compare.png)

#### 7071×7071 — последовательное быстрее

При кэш-эффективных стратегиях (строки, сетка) последовательное быстрее в ~1.7×: 1845 мс vs 3154 мс по строкам. Исключение — «По столбцам»: почти паритет (3888 мс vs 3955 мс), потому что кэш-промах бьёт оба варианта одинаково.

![7071x7071_compose](plots/compose/7071x7071_compare.png)

#### Вывод

Составное ядро выгодно, пока изображение помещается в кэш. На больших данных три прохода с маленькими ядрами обгоняют один с большим: параллельные потоки справляются с кэш-эффективным обходом быстрее, чем платят за дополнительную арифметику. Есть точка перелома: при двух фильтрах (34 vs 49 ops) составное ещё иногда выигрывало — с тремя (83 vs 169 ops) перевес арифметики стал слишком большим.
